# Prospective progression from a simple homework implementation

This sequence starts with the course compiler's single-workgroup implementation of both complete workloads. It performs ordinary explicit tensor, vector, normalization, attention and activation instructions, with direct HBM operand loads. It has no shared-memory weight retention or inter-SM work partitioning. It is a simple homework baseline, not the earlier one-scalar-output-per-thread maximum-flow example: the homework compiler already uses tensor matrix instructions and register tiles.

The target remains the fixed sixteen-SM, 32-vector-lane, eight-HBM-channel, no-cache homework hardware. A single-workgroup baseline deliberately leaves most SMs idle. The course's original 48-deep matrix tile touches up to 768 words in one register partition and is illegal when each partition holds 512 words. Baseline generation therefore uses m=8, n=8, k=16 matrix tiles; it retains all original workload mathematics and interface layouts. All source comes from a separately loaded copy of the official compiler. The authoritative parser, functional executor, race checker, scheduler and scorer are unchanged.

The second stage allows n in {8,16} and k in {16,32}, retaining m=8. Each register operand must fit 512 words. CP-SAT selects exactly one legal pair. Its objective prioritizes lower HBM input elements per output for a representative 64-by-256 times 256-by-256 dense multiplication, then fewer transfer launches. The weight 100000 makes the first term dominate across this finite set. The chosen n=16,k=32 configuration is a model proposal, not a measured improvement. Both complete workloads are regenerated and graded.

The third stage is a distinct shared-memory hypothesis. For prompt matrix products with more than eight output rows, load the whole K-by-16 weight panel into shared memory once, then reuse it across eight-row output tiles. Keep the selected register tile and ascending arithmetic order. Panels need at most 64 KiB. There is one buffer and no prefetch. Decode retains the preceding program exactly because a single output row cannot reuse a weight panel across row tiles. This stage is an exploratory mechanism probe, not a solver-certified performance optimum. The same evaluator can reject it if extra shared service outweighs HBM reuse.

Each immutable pair goes through the unchanged full seed-7 command-line grade, sequentially. The independent checking agent first audits expanded register addresses, source size, and file hashes. Each grade has a 30-minute wall-time cap and a 4-GiB process memory guard. Failure or timeout is preserved; no incomplete grade enters a performance curve. Full correctness and full eligibility are distinct: a simple correct program can fail the latency gate. Plot verified per-case cycles or speedups even if ineligible, but only eligible grades may improve the eligible score curve. The historical advanced incumbent is a separate reference, not a newly discovered result.

The shared homework clock starts before the earlier continuation work, basic-compiler inspection, implementation and generation. It is preserved in clock.json, so the basic branch's first data point occurs after actual preparation time. The preceding native RTX diagnostic and earlier baseline discovery are excluded explicitly. Each completed stage records its actual elapsed time; no timestamps are reconstructed from file modification dates.

This is a three-stage prospective sequence, not proof that all advanced mechanisms have been explored. Broader parallel scheduling and double buffering would require additional generated variants and complete checks. No performance estimate, partial operator test, or native-GPU measurement substitutes for the homework grade. No submission or Git push is requested for this study.
